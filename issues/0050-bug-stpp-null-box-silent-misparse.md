# 破損 MP4 の null 入り StppBox が黙って誤パースされる

- Priority: Medium
- Created: 2026-08-16
- Completed: {YYYY-MM-DD}
- Branch: feature/fix-stpp-null-box-silent-misparse
- Polished: {YYYY-MM-DD}

## 目的

破損 MP4 の stpp ボックスに null バイトが含まれる場合、コアの `Utf8String::decode` が null で読み止めるため、null 以降のバイトが後続フィールドとして誤解釈され、データ欠損が黙って進行する問題の挙動を確認し、対応方針を決める。

## 現状

コア (shiguredo_mp4 2026.4.0) の `Utf8String::decode` は null バイトで `break` して読み止める (エラーにはしない)。このため:

- stpp ボックスの `namespace` に null バイトが含まれると、null 以降のバイト列は `schema_location` の先頭として誤解釈される
- フィールドずれが発生し、データ欠損がエラーなしで進行する

これは 0031 (null 文字入り入力で panic する問題の修正) のレビュー中に発見した。0031 の修正は Python 側からの入力経路を塞いだだけであり、デマクス時の破損データ経路は対象外のまま。

なお、demux のパースエラーの Python 側への報告 (エラー隠蔽の解消) は別 issue (0036) で対応予定であり、本 issue はコア側の挙動確認と、バインド側で検出するならその実装を扱う。

## 設計方針

- まずコアのデコード挙動を実際に確認する (null 入り stpp ボックスのデマクス結果)
- コア側で修正すべき問題か、バインド側 (mp4-py) で検出・報告すべき問題かを判断する
- バインド側で対応する場合は、コアの `Utf8String` の null フリー不変条件を信頼せず、デコード結果を検証する方式を検討する

## 完了条件

- 破損 MP4 の null 入り stpp ボックスに対するデマクス挙動が確認され、対応の要否が判断される
- 対応が必要な場合は、黙っての誤パースを検出できる仕組みが実装される

## 解決方法

1. コアの `Utf8String::decode` と stpp ボックスのデコード経路を再確認する
2. 破損データ (null 入り stpp) のデマクス挙動をテストで再現する
3. 対応方針 (コア側 / バインド側 / 対応不要) を確定する
4. 必要な場合は実装し、テストを追加する
